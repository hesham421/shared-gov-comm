# Registry & Steering Builder — ENGINE

```
Engine        : Registry & Steering Builder
Stage id      : P-1
Pass          : bootstrap   (once per platform)
Questions     : forbidden
Lane          : analysis
Inputs        : domain-profile
Produces      : platform/project-registry.md   (ONLY this file)
Owns IDs      : — (registers candidates; assigns no pipeline ID)
Next          : P0
Profile       : commerce — COMMERCE
```

This engine bootstraps the platform registry from the saved `domain-profile.md`. It is
the first consumer of that file and the **creator** of `project-registry.md`; nothing
that runs before it may require a registry, and it asks no questions — every fact it
writes is extracted from its inputs and cited. The registry's categories are defined
in `shared/REGISTRY-SCHEMA.md` (Part A, domain-neutral); this engine fills them and
adds the **steering enforcement notes** that bind every later stage to the
domain-profile's vocabulary.

Completion (write → registry → analyze → commit) is owned by the orchestrator — see
`shared/GOVERNANCE-CORE.md`.

## 1 — Purpose and operating model

```
DOES
  - Reads analysis/domain/domain-profile.md completely (STEERING block first), then any
    platform brief supplied as input.
  - Reads an existing project-registry.md as the baseline when re-run (extend mode).
  - Extracts every governance-relevant fact into the registry categories (§3).
  - Copies the STEERING block into the registry's conventions section VERBATIM and
    writes the enforcement notes (§3.6).
  - Preserves every existing entry — keeps previously registered content. [G]
  - Emits the complete registry file — not a diff. [G]

DOES NOT
  - Invent information not present in the inputs, or pre-register modules/entities
    that are only mentioned in passing. [G]
  - Assign any pipeline ID (POL, US, REQ, AC, ENT, RULE, DBF, XM, CON, API, QR, UXD, SCR, SCR-REQ, TC, ADR, CS, FEAT) — IDs are assigned by their
    owning stages (`factory.ids.atoms.*.owner`). This engine registers CANDIDATES.
  - Generate implementation content (tables, columns, endpoints, screens).
  - Ask the user. A fact the inputs do not settle becomes an OPEN row in the
    open-question index (§3.5) with its evidence; the next stage that allows
    questions (P0) resolves it in dialogue.
  - Decide on its own. Where a choice is unavoidable (e.g. two plausible owners for
    one candidate), it records BOTH as candidates with Status OPEN — it does not pick.
```

Language policy: narrative in `en`; names and terms carry all of `ar, en`.

## 3 — Extraction rules (what goes where)

Category labels below are the ones in `shared/REGISTRY-SCHEMA.md`; the registry's own
section names map to them in its Schema Compliance Map (§5).

### 3.1 Domains and modules → module / component index
```
Look for : named business areas, functions, systems; any grouping of processes or
           data; any explicit system boundary (domain-profile §4 rows first).
Write    : one row per component the domain-profile names — module code, display
           name, bounded context, category, core/extension, Status.
Rules    : a module enters the index only when it is described as a scope boundary, [G]
           not merely mentioned; do not reuse a code already held by another row. [G]
```

### 3.2 Entities → entity ownership + shared-entity declarations
```
Look for : named business objects; data that is created, stored, retrieved, managed;
           objects with described attributes or relations; objects referenced by
           more than one component.
Write    : CANDIDATE rows (§6 format) — name, owner module, kind (one of
           master / transactional / lookup / config / security), PRIVATE / SHARED?, source.
Rules    : no entity ID here; unclear owner → Status OPEN + open-question row;
           referenced by several components → SHARED candidate in the shared
           declarations category.
```

### 3.3 Cross-module dependencies → the dependency graph (no rows here) [G]
```
The dependency index is `platform/dependency-graph.json`, DERIVED by `gov.py graph`
(shared/XM-PROTOCOL.md §3) from P0's `platform-dependencies` block, each SRS's
`module-dependencies` block and the XM registers. This registry writes no
dependency row: its compliance map points the category at that file. The relations the
domain-profile states (§6) reach P0, which turns them into the block.
```

### 3.4 Governance decisions → decisions log
```
Look for : confirmed technology, naming or structural choices; system-wide business
           rules; constraints from existing infrastructure (domain-profile §5, §8).
Write    : decision text + rationale + source. Only CONFIRMED decisions — not [G]
           options still under discussion.
Rules    : a decision this engine had to make itself is not a registry row — it is
           an ADR (`analysis/decisions/ADR-{MOD}-{seq:03d}.md`, see shared/GOVERNANCE-CORE.md)
           referenced from the registry.
```

### 3.5 Open items → open-question / escalation index
```
Look for : unresolved ownership; ambiguous boundaries; conflicting statements;
           an entity or process without a clear owner; a dependency the inputs
           cannot resolve (domain-profile §10).
Write    : question, evidence (both sides of a conflict), affected rows, Status OPEN,
           "to be resolved by P0 dialogue".
Rules    : this engine RECORDS open items; it does not resolve them by guess and does not [G]
           asks the user.
```

### 3.6 Steering → conventions section + enforcement notes
```
Copy verbatim from domain-profile §7:
  ubiquitous language table · bounded contexts · module prefixes · identifier rules
  · knowledge sources to cite
Then write the ENFORCEMENT NOTES:
  E1  Every later artifact uses these terms verbatim; a synonym listed under
      "do not say" is a consistency finding at the pass gate (`gov.py analyze`
      checks registry ↔ artifact agreement).
  E2  IDs follow `{prefix}-{MOD}-{seq}` (seq width 3) with the module codes of
      this section only. [G]
  E3  Entities are classified with the kinds `master, transactional, lookup, config, security`.
  E4  Sources to cite when a stage resolves an ambiguity: the knowledge sources
      listed here, then the domain-profile itself.
  E5  Pipeline status per module (category "pipeline / progress status") is
      maintained by the orchestrator from commits — this engine seeds the rows
      as NOT STARTED.
```

# Platform Brief — Retail & Wholesale Commerce SaaS on erp-core

**Status:** approved vision, input to `domain-profile` · **Owner:** Hesham Ezzat · **Date:** 2026-10-21
**Given:** `erp-core` (multi-tenant core, deployment mode `single|multi`, business modules tenant-agnostic) — consumed via `gov.py given add erp-core --version <current>`; nothing the core provides is rebuilt.
**Technical base (approved):** Spring Boot (Java 25) backend on `erp-core` · React frontend, one build for all deployments reading `GET /api/public/app-config` (tenancy mode, feature flags, activity preset) · PostgreSQL 16 (Flyway, app migrations `V1000+`). Jasper for printing via the core `PrintApi`.

---

## 1. One-paragraph vision

A SaaS platform for small and medium **retail and wholesale traders** in Egypt and the Gulf, covering back-office (purchasing, inventory, sales, receivables/payables, accounting, tax & e-invoicing), point of sale, and an **integrated e-commerce storefront** — one catalogue, one stock, one customer base. It serves many trading activities (electronics & appliances, apparel, household goods, cosmetics, grocery, spare parts, building materials, …) from **one codebase** through six activity capability flags and per-activity presets. It is **feature-complete but simple to use**: every capability exists, nothing is forced on the user; power lives in the backend, the UI shows only what is enabled.

## 2. Market and positioning (facts gathered 2026-09)

- Wholesale & retail trade is the largest activity by number of establishments: **54.4%** of Egypt's 3.9M establishments (6th Economic Census 2022/23) and **30.7%** of Saudi SMEs (Monsha'at SME Monitor).
- Demand is regulation-driven: **mandatory e-invoicing** (Saudi ZATCA phase-2 waves; Egypt B2C e-receipt expansion from Sept 2025) forces every small trader to adopt compliant software.
- Competitors in the segment are all SaaS (Qoyod, Wafeq, Daftra, …); the differentiator is **one product for back-office + POS + storefront**, activity-aware, and simple.

## 6. Simplicity as a requirement ("everything available, nothing imposed")

1. **Progressive disclosure**: every screen starts minimal; "Advanced" reveals the rest; ≤ 4 mandatory fields per screen.
2. **Presets then customise**: choosing the activity fills all settings; later changes never require re-setup. Flags may be turned **on** at any time; turning off is blocked when data depends on it.
3. **Only enabled is shown**: menus, fields, reports, and storefront features bound to flags — no dead menus.
4. **Action in place**: return from the invoice, collect from the statement, receive from the PO.
5. **No dead ends**: every error offers a next action; undo for unposted operations.
6. **One global search** (items, customers, documents).
7. **Mobile-first** for selling, collecting, counting; responsive web, no separate app in v1.
8. **Defaults ("everything available, nothing imposed")**: one warehouse/branch/currency/price list to start; every such dimension exists in the data model from day one (e.g. every stock move carries `warehouse_id`); the UI hides the selector while the count is 1 and reveals it — plus the related actions (e.g. inter-warehouse transfer) and report filters — automatically when a second one is added. No data migration, no "mode" switch.
9. **Setup wizard (5 steps)**: company → activity preset → tax & e-invoice → payment methods → import items from Excel.
10. **Metric**: an owner with no technical background completes setup and issues the first invoice in **≤ 30 minutes** without training; a new employee sells after **≤ 10 minutes**.

## 7. Coverage and architecture guarantees (how we know it is sound)

| Risk | Guarantee | Enforced in |
|---|---|---|
| Activity "covered" on paper only | One **conformance scenario per preset** (setup → receive → sell → return → collect → report) runs in CI | `activity-conformance` test suite |
| Behaviour varies by activity ad hoc | Logic reads the six flags via `FeatureFlags` only; every flag tested in both states | ArchUnit + lint (`activity ==` or preset read outside settings = build failure) |
| Missing requirement for an activity | **Flag × activity matrix** is a P0 artifact; each cell traces to an EARS requirement ID (P1) and a `TC-*`; an untraced cell fails the consistency check | Factory traceability P0→P1→test-gen |
| Random inter-module design | Fixed DAG (§5); `crossmodule` contracts only; core via manifest extension points | ArchUnit boundaries + `C-GIVEN-1/2` + pass-review checklist (`erp-core-usage`) |
| Decisions drift during build | §3 decisions enter P0 as fixed + ADRs; no open questions after the PRD | One-gate analysis + adversarial reading |
| Uncontrolled growth | Fixed delivery order; a module is Done with reports, tests, conformance green | execution-state gates |

**Definition of "covers activity X":** preset exists + conformance scenario green + every matrix cell traced. Adding an activity later = one matrix column + one scenario.
