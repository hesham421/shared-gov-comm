## PROPOSALS (round 1)

**PROPOSAL: P-1 — Trace for catalogue-content stories with no dedicated policy**
- Affects: US-CAT-002, -013, -014, -015, -016, -018, -021
- Options: A) Trace each one to POL-CAT-001. The entities are the content of the one catalogue that every channel uses. B) Skip them and ask P0 for new POLs in a later version. The cost is a PRD with no story for 6 of the 9 registry entities, so P1 would have no need to derive REQs from.
- Researched: Engine §3 says "each entity owned → 'the [role] needs to manage [entity]' is a legitimate seed". The TRACES RULE only demands at least one POL. KB §1 says "one catalogue, one stock, one customer base" and lists back-office, POS and storefront as the consumers. Registry OI-08, OI-10, OI-11 and OI-15 tie each entity to a channel need: POS scanning, storefront browsing, and e-invoices issued from every channel.
- **Recommended: A.** Each of these stories states the channel it serves, and the trace is the policy that the entity fulfils.

**PROPOSAL: P-2 — Priority basis**
- Options: A) "—" on every story, because CAT ships whole in wave 1 (D10). B) Assign priority from what the knowledge base states or clearly implies. HIGH: the §6 simplicity requirements (D9 makes them measurable), the regulation-driven e-invoice data (§2), and variants and bundles, which the launch presets require (§4.2: apparel ✓ variants, electronics ✓ bundles). MEDIUM: storefront-facing stories, because the storefront goes live in wave 2 (§8.2). LOW: weighed items, because produce by weight is outside the stated launch priority (§4.2). "—" for everything else.
- **Recommended: B.** This is the engine's rule ("only if stated or clearly implied") applied story by story. It still keeps every story in CAT's wave-1 delivery.

**PROPOSAL: P-3 — Item-name language rule (OI-12)**
- Options: A) Write a NEED story (US-CAT-008) tracing POL-CAT-006 and POL-CAT-001, and leave "Arabic mandatory, English optional" to P1 as the rule. B) Put the rule into the PRD as text.
- Researched: The registry says OI-12 is "applied by P0.5 as a standard language rule; not a client-specific POL". Engine §8 forbids field-level constraints in the PRD. KSA VAT Implementing Regulations Art. 53 requires the tax invoice in Arabic.
- **Recommended: A.** The rule is recorded in RESOLVED DECISIONS so that P1 can cite it.

**PROPOSAL: P-4 — Standard values of `einvoice-item-code-type`**
- Options: A) GS1 and EGS. B) Also add a ZATCA-specific type.
- Researched: The Egypt ETA e-invoice SDK `itemType` takes `GS1` or `EGS`. ZATCA's UBL uses an optional standard item identifier (GTIN) and has no separate code-type list. The barcode on the variant already covers that identifier.
- **Recommended: A.** These are the standard values the registry delegated to P0.5. They are mdl lookup values, not new IDs.

**PROPOSAL: P-5 — Catalogue change history and catalogue permissions**
- **Recommended: no story.** Permissions are a P1 permission matrix (engine §8). Change history is behaviour of the given `audit` module, and no CAT policy states it as a need. If the trader needs it, P0 adds a POL in a later version.

**PROPOSAL: P-6 — Scope exceptions (pre-assembled kits, activity-specific models, multi-vendor catalogue)**
- **Recommended: no DEFERRED stories.** These items were already decided as exclusions in business-policies SCOPE EXCEPTIONS. DEFERRED is for items the user will not decide (engine §4), and these are decided. The DEFERRED table points to them.
