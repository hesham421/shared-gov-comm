I've written both P2 files for PTY v1. I haven't run `gov.py analyze` or executed the SQL; the orchestrator runs those. One thing needs your call: I recorded the five new ADRs inside the script rather than as files, because the brief allowed only these two files.

**The design:**
- **Tables:** five, one per entity: `PTY_PARTY`, `PTY_CUSTOMER`, `PTY_SUPPLIER`, `PTY_ADDRESS` and `PTY_CREDIT_OVERRIDE_REQUEST`. Every primary key uses `GENERATED ALWAYS AS IDENTITY` (BIGINT).
- **Columns:** 67, numbered `DBF-PTY-001` to `DBF-PTY-067`. Each one traces to an entity field and at least one requirement. Customer and Supplier have no name or code columns of their own; they read them from the Party table, as the SRS says.
- **Cross-module dependencies:** none. The SRS says PTY consumes nothing from other business modules. Links to the core's user records (`SEC_USER_ID`, `DECIDED_BY`) have no database constraint and are not cross-module dependencies.
- **Business rules in the database:**
  - 16 checks: name required, email and mobile format, payment terms 0–365, credit limit ≥ 0, the walk-in customer's restrictions, sale amount > 0, request result and status values, rejection reason, and decided/used fields.
  - Uniqueness: Party code, one Customer and one Supplier per Party, one store account per Customer, address code within a Party, and request number.
  - Three conditional unique indexes: email among active Parties (ignoring case), one walk-in customer, and one active default address per type.
- **Indexes:** 15 more, on foreign keys, search filters, and a "carries credit" index used by the `b2bCredit` switch-off count.
- **Seed data:** the 5 PTY lookup keys and their 16 values go into the core's lookup tables (`MDL_LOOKUP_TYPE`, `MDL_LOOKUP_VALUE`). Re-running inserts nothing twice.

**New ADRs (`ADR-PTY-018` to `022`):** none of them blocks the stage, and the pass continued.
- **018:** money columns are `NUMERIC(18,3)`, to cover 3-decimal Gulf currencies. Payment days are `INTEGER`. Lookup codes are `VARCHAR(50)`.
- **019:** `createdBy`/`updatedBy` hold the login name the platform fills in (`VARCHAR(100)`), as the engine rule requires. The SRS calls them BIGINT user references, so this departs from the SRS. `decidedBy` and `secUserId` stay BIGINT.
- **020:** no currency column, even though profile check CM-8 asks for one. The approved SRS says all PTY amounts are in the tenant's base currency.
- **021:** no tenant column. The core keeps tenants apart, so the per-tenant uniqueness rules are written without one.
- **022:** I guessed the column names for the core lookup tables. That table design wasn't in the brief and I wasn't allowed to look it up, so the seed block may not run as written. The backend stage (P3.1) must check those names against the real core tables.
