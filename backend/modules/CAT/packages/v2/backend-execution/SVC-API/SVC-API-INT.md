### API-CAT-049 — import items
Entity       : ENT-CAT-001, ENT-CAT-002, ENT-CAT-009 · operation CREATE · serves SCR-REQ-CAT-004 "submit file (custom)", "read result"
Honours: CON-CAT-001, CON-CAT-002, CON-CAT-005, CON-CAT-018
Endpoint     : /api/v1/cat/item-imports   verb: POST
Layers       : CatItemImportController.submit → CatItemImportService.importItems
Request      : body ItemImportRequest {fileDocumentRef: int64 required} · application/json; the client uploaded the xlsx beforehand through the given FILE endpoint (private storage), which returned fileDocumentRef (ADR-CAT-056) · each data row maps to nameAr (DBF-CAT-003), nameEn (DBF-CAT-004), baseUomCode (DBF-CAT-006), category code → categoryFk (DBF-CAT-015), brandCode (DBF-CAT-007), taxClassCode (DBF-CAT-008), einvoiceCodeTypeCode (DBF-CAT-009), einvoiceCode (DBF-CAT-010), GTIN barcodeValue (DBF-CAT-110), descriptionAr (DBF-CAT-011), descriptionEn (DBF-CAT-012)
Response     : 200 · ApiResponse<ImportResult> · paginated: no
Validations  : fileDocumentRef names an available FILE document of the caller's tenant (`FileDocumentLookupApi.isAvailable`; otherwise CAT-404-NOT-FOUND) · RULE-CAT-044 (xlsx and ≤ 10 MB — the file's type and size, like its bytes, are read through the core once CORE-GAP-file-document-metadata-read is answered: a delivery dependency, ADR-CAT-076; ≤ 5,000 data rows and a header equal to the sheet — otherwise the whole file is rejected) · RULE-CAT-045 per row: the checks of rules 001, 002, 003 (also against earlier valid rows of the file), 006, 026, 029 (also against earlier valid rows of the file), 030, 032 (the GTIN does not begin with the key of an active scale label layout; reported on column GTIN barcode — AC-CAT-166) and 042 — each failure reported through CAT-200-IMPORT-ROW-REJECTED with the failed rule's message as {reason} · a failing row is skipped and reported (row, column, reason in ar and en); for a name repeated inside the file, the RULE-CAT-003 {code} of the later row is the code the write pass gave to the earlier row's Item, so the rejection reasons are composed after the write pass · a GTIN repeated inside the file is rejected on the later row, column GTIN barcode, with the RULE-CAT-029 message as {reason}, where {code} is the code the write pass gave to the earlier row's Item — composed after the write pass, as for RULE-CAT-003; a GTIN that equals a stored active barcode takes {code} from QR-CAT-048 (the owning Item) · empty cells take defaults, filled cells are validated: an empty baseUomCode cell takes PIECE and an empty taxClassCode cell takes STANDARD (D-09); a non-empty baseUomCode or taxClassCode cell is validated under RULE-CAT-006 (an active value of CAT_UOM / CAT_TAX_CLASS, else the row is rejected for that column) and is never overridden by the default · RULE-CAT-005 · RULE-CAT-049
Errors       : CAT-400-REQUEST-INVALID, CAT-401-UNAUTHENTICATED, CAT-403-FORBIDDEN, CAT-404-NOT-FOUND, CAT-500-SERVER-ERROR, CAT-422-IMPORT-FILE-REJECTED, CAT-200-IMPORT-ROW-REJECTED, CAT-500-CODE-NOT-ISSUED, CAT-500-CHANGE-NOT-SAVED
Orchestration : check availability (`FileDocumentLookupApi.isAvailable`) → read the file's type, size and bytes and accept it (RULE-CAT-044) — **core dependency**: erp-core 1.6.0 publishes no read of an uploaded document's metadata or bytes, so this step is wired on the read the core publishes in answer to CORE-GAP-file-document-metadata-read (ADR-CAT-076); until then the import is not delivered, and CAT opens no storage client, issues itself no download token and makes no HTTP call to the FILE endpoints → validation pass, no write: per row resolve the category code (QR-CAT-032), check names, lookups (MdlLookupApi), e-invoice pair, name uniqueness (QR-CAT-002 + in-file set), barcode uniqueness (QR-CAT-048 + in-file set: the first valid row that carries a GTIN keeps it, every later row that repeats it is marked rejected under RULE-CAT-029 and points to that first row), GTIN format and scale prefixes (QR-CAT-059) → write pass in one transaction: take the scale-prefix lock once, at its start, when the file holds a GTIN row (QR-CAT-074), re-read the active layouts under it (QR-CAT-059) and re-check the GTIN rows in memory → re-read every Category referenced by a valid row with QR-CAT-032 FOR SHARE (in categoryPk order, after the scale-prefix lock) and reject each row whose Category is now inactive with RULE-CAT-026 (column category, reported through CAT-200-IMPORT-ROW-REJECTED with the RULE-CAT-026 message as {reason}) before its batch is saved, so no imported active Item points to an inactive Category (RULE-CAT-026, A7 invariant 2, ADR-CAT-059) → process the remaining valid rows in batches of 500: draw the batch's Item codes (CAT_ITEM) and Variant codes (CAT_VARIANT) from NumberSeriesApi before the batch is saved — one `next` call per code, because erp-core 1.6.0 publishes no block allocation (CORE-GAP-number-series-block-allocation.md, ADR-CAT-071) — then, under one savepoint, save the batch's rows as entities through QR-CAT-003, QR-CAT-011 and QR-CAT-049 (one INSERT per record under the given tenant filter; the identity keys rule out JDBC batching, and no JdbcTemplate or native statement is used — ADR-CAT-074) and flush at the end of the batch; on a unique violation the batch is rolled back to its savepoint and replayed row by row, each row with its own savepoint, reusing the codes already drawn → per row: Item with code from CAT_ITEM (DBF-CAT-002), itemKindCode STANDARD (DBF-CAT-005), baseUomCode (DBF-CAT-006) and taxClassCode (DBF-CAT-008) from the row, PIECE / STANDARD only where the cell is empty (D-09), publishStateCode UNPUBLISHED (DBF-CAT-013), isActiveFl true (DBF-CAT-014) (QR-CAT-003) → default Variant with code from CAT_VARIANT (DBF-CAT-023), isDefaultFl true (DBF-CAT-024), isActiveFl true (DBF-CAT-027), itemFk (DBF-CAT-028) (QR-CAT-011) → GTIN barcode with barcodeTypeCode GTIN (DBF-CAT-111), uomCode the base unit (DBF-CAT-112), variantFk (DBF-CAT-114), isActiveFl true (DBF-CAT-113) (QR-CAT-049) → record cat.CatalogueChanged CREATED per record → compose the in-file rejection reasons of RULE-CAT-003 and RULE-CAT-029 with the code the earlier row's Item received → return rows read, Items created, rows rejected and the rejections (ADR-CAT-048)
Repository   : QR-CAT-032 FIND_ONE (validation pass: no lock; write pass: FOR SHARE) · QR-CAT-002 EXISTS · QR-CAT-048 EXISTS · QR-CAT-059 FIND_ALL · QR-CAT-074 NATIVE (scale-prefix lock, once per import) · QR-CAT-003 SAVE · QR-CAT-011 SAVE · QR-CAT-049 SAVE (entity saves, one INSERT each, flushed per batch of 500 — no JDBC batching, ADR-CAT-074) · join NONE · READ_WRITE
Concurrency  : lock order — the scale-prefix lock (QR-CAT-074) first (when the file holds a GTIN row), then the referenced Category rows FOR SHARE (QR-CAT-032, in categoryPk order), both held until the commit; a Category deactivated between the two passes is caught by the write-pass re-read and its rows are rejected with RULE-CAT-026, and a deactivation that starts after the re-read (API-CAT-024, FOR UPDATE) waits until the import commits, so an imported active Item never points to an inactive Category; a name or barcode taken by a parallel request between the two passes hits UQ_CAT_ITEM_NAME_AR / UQ_CAT_BARCODE_VALUE; the batch is replayed row by row and the row's own savepoint is rolled back, so only that row is reported rejected (RULE-CAT-003 / RULE-CAT-029); a number-series failure rolls the whole import back (RULE-CAT-005); the scale-prefix lock is taken once per import, not per row, and is held until the commit, so a layout create (API-CAT-032) waits at most the import's 120 s limit · Time budget (ADR-CAT-071, ADR-CAT-074): the target for a file of 5,000 valid rows is 60 s on the reference deployment (validation pass ≤ 15 s, write pass ≤ 45 s) — a budget to be measured by TC-CAT-217's undelayed run, not a guarantee, because the write pass saves one entity per record; the guarantee is the hard limit: the service transaction carries `@Transactional(timeout = 120)` and the request timeout of the endpoint is 120 s. When 120 s is exceeded the transaction is rolled back as a whole: no Item, Variant or barcode is stored and no catalogue-change event is delivered (RULE-CAT-049), the codes already drawn stay as gaps in the series (the given's REQUIRES_NEW allocation), the scale-prefix lock and the Category share locks are released, and the answer is CAT-500-CHANGE-NOT-SAVED (REQ-CAT-139, AC-CAT-161); the owner imports the file again, split into smaller files
Security     : SCR-REQ-CAT-004 Item import · PERM_CAT_ITEM_IMPORT_CREATE
Localization : rejection reasons in ar and en (CAT-200-IMPORT-ROW-REJECTED wraps the failed rule's message)

#### In-process contract surface — `com.erp.cat.crossmodule.CatalogueReadApi` (ADR-CAT-045)
Other modules reach CAT only through this injected interface (`conventions.module_interface: in_process`). Each method calls `CatCatalogueReadService`, the same read service the endpoint's facade calls, so both surfaces return the same data (ADR-CAT-061). The read service carries no `@PreAuthorize`: the **calling module authorizes its own caller** against its own permissions before it calls CAT (SFR a shopper, SLS a cashier). The HTTP facades keep the screen permission, except `CatSearchQueryFacade.searchCatalogue`, which carries only `@PreAuthorize("isAuthenticated()")`. `searchCatalogue` is the one method whose read service checks `PERM_CAT_ITEMS_VIEW` of the current principal, in code, and answers an empty list without it (REQ-CAT-127), on both surfaces. Tenancy applies to every call. No HTTP client exists between modules.
