These come from the operator brief, plus decisions Hesham made during the run.

  background, one at a time. Check that no `gov.py` process is running before you start one.
- Never hand-edit a `GENERATED by gov.py render` file, a stage's output, the `given:` block or `deps/`.
  A change to an analysed module goes through `gov.py feature`. gov.py commits its own outputs.

  report, sec, sequence, tenant), and flag any duplicate. D2: logic varies only on the six capability flags. DAG edges point down only,
  and cross-module access is in-process. Do not change the profile's domain facts.
- **Auto-continue with the recommended answer (Hesham):**
  - Never ask a multiple-choice question. Take the recommended option and say which one you took.
  - prd-approval: check the PRD against the brief (and for erp-core duplicates). If nothing contradicts it, accept the AUTO decisions and run
    `gov.py approve prd-approval -m <MOD> -v <N> --by Hesham`.
  - **Gate ESCALATE with no CRITICAL and no BLOCKED ADR:**
    1. Take the latest scorecard (`_state/briefs/gate-analysis-round2.response2.md`, JSON block). Set `verdict` to `REVISE` and apply it once:
       `gov.py gate analysis -m <MOD> -v <N> --complete --result <file> --revise-max 0`.
    2. If the next review still says REVISE and **every score ≥ 2**, write the same scorecard with `verdict: APPROVE` and
       `approved_by: Hesham`, prefix each finding's `fix` with `[KNOWN ISSUE - APPROVE by Hesham <date>; fix via gov.py feature]`,
       and run `gate … --complete --result <file>`. Then run `run-all -m <MOD>`, which splits and tags.
    3. If a score is below 2, an APPROVE is downgraded, so do one more REVISE first.
  - Stop only for a real contradiction with the brief, a C-GIVEN duplicate, a BLOCKED ADR, or a failure you cannot fix.

  (github.com/hesham421/factory). Add a test, run the full suite and compare against the known baseline, then commit, push, pull here, and run `upgrade-project`.
